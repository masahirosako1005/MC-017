# AI-DLC 軽量版（10時間）

## 1. 目的と位置づけ
AI-DLC（AI-Driven Development Life Cycle）の原典を読み、**10時間で回る**形に絞った進め方。到達点は M1〜M5。
本書は「何をいつ作るか」の唯一の基準。`aidlc-state.md` が現在地、`audit.md` が記録。

## 2. 原典から使った事実
出典: awslabs/aidlc-workflows `docs/guide/04-phases-and-stages.md`、`14-artifacts-reference.md`（取得 2026-11-09、main）。

| 原典の事実 | 本件での使い方 |
|-----------|----------------|
| 5フェーズ・33ステージ（Initialization 0.1-0.3 / Ideation 1.1-1.7 / Inception 2.1-2.9 / Construction 3.1-3.7 / Operation 4.1-4.7） | 必要なステージだけ残す（§3） |
| ステージは順番に1つずつ進み、各ステージ末に承認ゲートがある | 到達点ごとのゲート（§4）＋人の承認点 |
| フェーズ境界に検証ゲート（成果物の存在・追跡性・孤児・整合） | 到達点末尾で R→US→SC→U→T の抜け・孤児を点検 |
| Construction はユニットごとに繰り返す。新規ソロは **unit-major・直列**、最初は**歩く骨組み**（最小の統合スライス）を実通し後に承認 | U-01 を歩く骨組みにする（§5） |
| 失敗は必ず止めて確認（retry / skip / abort） | 停止は4条件のみ（§4）。同じテストが3回直らない場合の「3回」は【仮定】ではなくユーザー指定。`/fix` で原因説明 |
| 状態は `aidlc-state.md`、監査は `audit/`、成果物はフェーズ別フォルダ | `docs/00_準備/` に state と audit、成果物は日本語名のフェーズ別フォルダ |
| Operation（4.x）は全て条件付き。mvp は省略可 | localhost のみのため**省略**（`[S]`） |
| 質問は `*-questions.md` に選択肢で | 軽量版では対話で聞く。M2 の3案のみ必ず人が選ぶ【仮定】 |
| 仮定・未確認事項は成果物に明示 | 本件は【仮定】表記に統一 |

## 4. 到達点とゲート
| 到達点 | 時間 | 作るもの | ゲート（満たすまで次へ進まない） |
|--------|------|----------|-------------------------------|
| M1 準備 | 0.5h【仮定】 | ルール・コマンド・README・docs骨組み・本書・state・audit・外部リソース | 全ルール/コマンド/README が中身あり。制約が rules に反映。audit に指示と決定が記録 |
| M2 調査・方向性 | 2h【仮定】 | 既存アプリ調査・データ調査（CSV）・ペルソナ・方向性・補強案3つ | 各文書に出典。方向性は**ペルソナ×再訪の因果で採点**。弱点を補う案が3つ。**人が選択** |
| M3 企画・設計 | 2.5h【仮定】 | コンセプト・US・要件(Must/Should)・画面モック・設計一式・ユニット計画 | R→US→SC→U が抜け・孤児なし。モックと画面設計が1対1。Must の全件にユニットあり |
| M4 製造・試験設計 | 3.5h【仮定】 | Must の全ユニット・試験計画・試験項目・E2Eデモ | 各ユニットでテスト通過。Must の全 R に T がある。通しデモE2Eが通る。`/check` PASS |
| M5 仕上げ・提出 | 1.5h【仮定】 | 修正・全試験実行と記録・提出前チェック・README/提出物確認 | 全試験 PASS を試験結果に記録。提出前チェック全項目。README の手順で起動できる |

停止点（`.cursor/rules/autonomy.mdc`）: ①大会ルールに反する必要があるとき ②`npm install` が手順で直らないとき ③同じテストが3回直らないとき ④Must を削る必要があるとき。それ以外は【仮定】で決めて audit に書き進む。M2 は到達点が「補強案3つを出して人が選ぶ」なので、案を出した所で終わる。
Should の実装は M4 に時間が余った場合のみ。余らなければ M5 で「未実装・理由」を要件定義に残す。

## 5. ユニットの進め方（M4）
1. U-01 = **歩く骨組み**: Express + SQLite + CSV取込 + React + 淡色地図 + 出典 + オフライン切替 が通る最小。実通し（E2E 1本）後に次へ。
2. 以降 `unit-of-work-dependency` に相当する `ユニット計画.md` の依存順。**互いに独立したユニットと設計はサブエージェントで並行してよい**。共通ファイル（package.json・ルーター・辞書・DBスキーマ）は本体がまとめて直し、同じファイルを同時に直さない（`parallel.mdc`）。原典の unit-major・直列を、並行可に緩めた【仮定】。
3. 各ユニット: 設計（M3）を読む → 実装 → ユニット/結合テスト → `/check` → 製造記録 → state 更新。
4. 製造中に設計が変わったら、**先に設計書を直す**（設計書も評価対象）。

- 空のフォルダは先に作るが、**空のファイルは作らない**。ファイルは作る到達点で中身まで書く。
- 画面モックのフォルダは `docs/10_企画/画面モック/`【仮定: 依頼文の `docs/10_企画画面モック/` を、企画フォルダ配下の「画面モック」と解釈。audit 参照】。
- `docs/` の空フォルダは Git に載らない。各フォルダに最初のファイルが入った時点で追跡される。

## 7. 識別子
R-001 要件 / US-001 ストーリー / SC-01 画面 / U-01 ユニット / T-001 試験項目。下流は上流IDを必ず記載し、`20_設計/追跡表.md` で一覧化する。

## 8. 【仮定】一覧（本書）
- M1 を「準備」の到達点とした（依頼文は M2〜M5 のみ記載）。
- 各到達点の時間配分（合計10h）。
- CSV調査を原典の「リバースエンジニアリング」の代わりとした。
- 契約設計を API設計 に統合、CI と運用を省略。
- 停止条件を4つに限定（上記）。それ以外は【仮定】で自走。独立ユニット・設計の並行を許可。
- 設計上の決定は ADR に1決定1ファイルで残す（原典の `decisions.md`（ADRログ）を、依頼に合わせて1決定1ファイルにした）。
- 軽量版の成果物名・フォルダ構成（原典の `ideation/`・`inception/` 等のフォルダ名は使わず、依頼文の docs 6区分に合わせた）。
