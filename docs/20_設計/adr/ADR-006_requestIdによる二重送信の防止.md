# ADR-006 requestId による二重送信の防止
- 状態: 採用
- 日付: 2026-11-09
- 対応: R-053 / R-017 / R-025 / AC-060 / AC-061 / U-01
## 背景
ユーザー指示（14:00）で試験に二重送信を入れる。さいころを2回送ると回数が2回減り、クーポンを2回送ると…など、操作の重なりで記録が壊れうる。ネットが不安定だと再送も起きる。
## 決定
状態を変える POST（QR・ひとこと・誘う・振る・クーポンを使う・予言に答える・デモで回数を足す）は body に `requestId`（UUID v4、36字）を必須にする。サーバーは同じトランザクションで `requests(user_id, request_id)` を確かめ、あれば保存した応答をそのまま返し、無ければ処理して応答を保存する。画面は押した時に `requestId` を作り、応答が来るまでボタンを `aria-disabled` にして2回目を送らない。
## 理由
一意キー（`grants` など）だけでは「さいころを2回振る」を区別できない（2回とも正しい操作でありうる）。`requestId` なら「同じ1回の操作」かどうかが分かる。
## 検討した代替案（採らなかった理由）
- 画面でボタンを止めるだけ: API を直接2回送ると壊れる。
- 時間で間引く（例 1秒に1回）: 正しい連続の操作も止めてしまい、試験しにくい。
## 結果・影響（良い点・悪い点・注意）
良い点: 再送しても1回分だけ。悪い点: `requests` 表が増え続ける（デモの規模では問題ない【仮定】）。注意: 同じ requestId で中身の違う要求は、保存した応答を返す（後の中身は使わない）。
## 【仮定】（資料にない前提。無ければ「なし」）
保存した応答の期限は設けない。
