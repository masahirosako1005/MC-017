# ADR-005 ダミー ID はヘッダで送り、Origin を確かめる
- 状態: 採用
- 日付: 2026-11-09
- 対応: R-001 / R-052 / R-057 / U-01
## 背景
ログインなし・1端末1人（competition ルール）。サーバーは利用者ごとの回数・盤・クーポンを持つ。Cookie を使うと、別のサイトから localhost へ状態を変える要求を送られるおそれがある（SEC-NODE-13）。
## 決定
1. クライアントが初回に `guest-` ＋英小文字・数字6字を `crypto.getRandomValues` で作り `localStorage` に置く。
2. API には `X-Guest-Id` ヘッダで送る。サーバーは `^guest-[a-z0-9]{6}$` で検証し、`POST /api/session` で無ければ作る。
3. 状態を変える要求（POST・PUT・PATCH）は、`Origin` があって自分（`http://127.0.0.1:PORT`・`http://localhost:PORT`）以外なら 403。JSON 以外は 415。
4. 利用者 ID を URL や body で受けない。クーポンと予言は `X-Guest-Id` と持ち主が合うときだけ返す。
## 理由
独自ヘッダはフォームやリンクからは付けられず、別オリジンの fetch では CORS の事前確認が要る（CORS は開かない）。個人情報が無いので、ID は推測されにくい長さで足りる。
## 検討した代替案（採らなかった理由）
- Cookie: CSRF の対策が要る。ログインに近づく。
- URL に ID: ログ・履歴に残る。
## 結果・影響（良い点・悪い点・注意）
良い点: 認証を作らずに利用者を分けられる。悪い点: ID を知っていれば同じ利用者として扱える（個人情報は無く、ダミーのため許容【仮定】）。注意: 端末を替えると続きは消える（ペルソナ P-05 の弱点、方向性 §9）。
## 【仮定】（資料にない前提。無ければ「なし」）
ID の長さ6字（36^6 通り）で十分とみなす。
