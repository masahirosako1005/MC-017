# SC-A07 設定（画面設計）

作成: 2026-11-09 15:33（実測） / 位置づけ: 追加企画（運営画面）。要件定義へは未反映 / モック: `docs/10_企画/画面モック/SC-A07_設定.html`（1対1。見た目の正は `admin.html#a07`。モックの見出しは「設定（盤・特典・ボーナス）」）
上流: 運営向け画面_仕様案 §2（観光協会が変えられるもの）、§5（SC-A07、Should）、§5.1、§8（GET・PUT `/api/admin/settings`）、§9（設定の変更）、§11.3（店の特典マスを作れる人数の閾値）。二重送信は ADR-006、アプリ内の今日は ADR-008。

## 1. 目的
**「どうしたら再訪につながるか」**を、数字を見たあとに**手を打つ**画面。再訪とみなす日数・再訪ボーナス・次回クーポンが使えるまでの日数・期限・店の特典マスを作れる人数を、季節や混み具合に合わせて変える。変更は「適用する日」から使い、すでに配ったクーポンは変えない。前と後を履歴に残し、SC-A09 の施策と同じく、変えた後に数字が良くなったかを追えるようにする。

| 読み込み中 | フォームの欄と履歴の表に灰色の枠と「読み込み中…」。［変更を保存］は押せない（`aria-disabled="true"`） | 待つ |
| 空（履歴0件） | 変更の記録に「まだ変更はありません。」【仮定】。フォームは今の値（既定値）で出す | — |

| 1.3.5 | 個人の情報を入れる欄は無い（対象外の根拠: 入れるのは設定の数と日付だけ） |

| 2.4.3 | ダイアログを開くと中へ、閉じると［変更を保存］へフォーカスが戻る。誤りがあれば最初の誤りの欄へ |

| 3.3.4 | 変更の前に「前と後」の確認を1回。適用前なら新しい保存で置き換えられる |

- 使いにくくなる人と対策（INC-01）: 数字を打ち間違えやすい担当→範囲を欄の下に書き、保存の前に前と後を見せる。変更の影響が分かりにくい人→「すでに配ったクーポンは変わりません」を説明とダイアログの両方に書く。
- だれのための工夫か（INC-03）: 前と後の確認は数字に不慣れな担当のためだが、複数人で設定を引き継ぐときの記録（履歴）としても役立つ。

## 9. 試験で確かめる観点（仕様案 §9 から。合否は書かない）
- 設定の変更: 適用する日より前に配ったクーポンの「使えるまで」「期限」が変わらない。適用する日からの訪問・クーポンに新しい値が使われる。
- 二重送信: 同じ `requestId` で2回送っても、履歴が2行にならない。
- 入力: 範囲の境界（`revisitDays` 3 と 60 は通る、2 と 61 は 400）、小数・文字列・未知キー・`effectiveFrom` が今日は 400。`campaignThreshold` 4 と 101 は 400。
- 権限: 店舗の役割で GET・PUT とも 404、`ADMIN_MODE` なしで 404。別オリジンの PUT は 403。
- 指標の計算: 再訪とみなす日数を変えても、すでに記録した訪問の種類（`visits.kind`）は変わらない【仮定】。
- アクセシビリティ: キーボードだけで変更・確認・保存ができる、誤りが文字で出る、200% 拡大で横に流れない。

## 10. 【仮定】
- PUT の入力に `campaignThreshold: 5〜100` を足す（仕様案 §11.3 で SC-A07 から変えるとあるが、§8 の入力に無い）。
- 🎁マスのクーポンの並びは、この版では見るだけで変えられない（仕様案 §5 は「並び」も設定に挙げているが、モックは見るだけ）。
- ［元に戻す］はフォームを今の値に戻すだけ。保存した変更の取り消しは、前の値で新しく保存する。
- 確認のダイアログの文言とボタン（15:45 にモックへ見本を追加）。
- 適用前の変更は1つまで。新しく保存すると前の予約を置き換え、履歴に残す。履歴の「適用前」の印。
- 変更の記録の表に caption「設定の変更の記録」を付ける（15:45 にモックへ追加）。
- 再訪とみなす日数を変えても、すでに記録した訪問の種類は変えない（適用する日からの訪問だけ新しい日数で判定）。
- この画面では上の帯の期間を出さない。
- 読み込みに失敗したときはフォームを出さない、変わった項目が無いときは保存しない、などの文言。
