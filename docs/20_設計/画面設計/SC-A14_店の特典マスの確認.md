# SC-A14 店の特典マスの確認（画面設計）

作成: 2026-11-09 15:34（実測） / 位置づけ: 追加企画（運営画面）。要件定義へは未反映 / モック: `docs/10_企画/画面モック/SC-A14_店の特典マスの確認.html`（1対1。見た目の正は `admin.html#a14`）
上流: 運営向け画面_仕様案 §2（観光協会だけが確認）、§5（SC-A14・【仮定】Should）、§7（US-112）、§8（GET `/api/admin/campaigns`・POST `/api/admin/campaigns/:campaignId/review`）、§9（店の特典マスの権限）、§11.4（作り方の決まり）、§11.6（観光協会の確認）、§11.7（状態）。

## 1. 目的
店が作ったイベント・クーポンは**旅行者全員の盤に出る**。観光協会の担当が、盤に出す前に、誤解を招く表現や連絡先が無いか、同じスポットが店のマスばかりにならないかを確かめ、承認するか、理由を付けて差し戻す（US-112）。旅行者にとって「次に来る理由」の特典マスが信頼できるものであり続けることが、「**どうしたら再訪につながるか**」の土台になる。

- 店の文字（名前・内容・品名）は、作るときに URL・メール・電話番号の形をサーバーが拒否している（SC-A13 の 6o）。それでも表現の確かめは人がする（例: 誤解を招く「無料」の言い方、連絡先らしい書き方）。
- 承認したキャンペーンは、始まる日に `approved → active` になる（§11.7）。承認する時点で始まる日を過ぎていたら承認できない（4. 状態）。

## 4. 状態
| 状態 | 画面 | 次の行動 |
|------|------|----------|
| 読み込み中 | カードと記録の表の場所に灰色の枠と「読み込み中…」 | 待つ |
| 空（確認待ち0件） | カードの場所に「いま確認待ちのキャンペーンはありません。」。記録の表は出す | — |
| 空（記録0件） | 記録の表の代わりに「まだ確認の記録はありません。」 | — |
| エラー（読み込み） | 「確認待ちを読み込めませんでした。」と「もう一度」 | もう一度 |
| エラー（理由が無い・長い） | 差し戻しで理由が空・100字を超えるとき、欄の下に ⚠ と「差し戻す理由を1〜100字で書いてください」。欄にフォーカスを移し、`role="alert"`。確認のダイアログは開かない | 理由を書く |
| すでに確認された（409） | ほかのタブ・ほかの担当が先に承認・差し戻ししていたら「このキャンペーンは、すでに確認されています」と出し、一覧を取り直す | 記録を見る |
| 始まる日を過ぎた（409） | 「始まる日を過ぎたため承認できません。差し戻して、店に日を直してもらってください」【仮定】 | 差し戻す |
| 重なりの警告 | 3b の文を出す。承認はできる | 確かめて決める |
| 送信中 | 「承認する」「差し戻す」と、ダイアログの［承認する］［差し戻す］は押せない（`aria-disabled`）。2回押しても `requestId` で1回だけ（記録も1行） | 待つ |
| オフライン | 同じ PC のサーバー（127.0.0.1）なので、ネットが切れても確かめて決められる。表示は変えない | そのまま使う |
| 権限なし | `ADMIN_MODE` なしは 404。店舗の役割で GET `/api/admin/campaigns`・POST review を呼ぶと 404（「店の役割では承認できない」、仕様案 §9）。店舗のメニューにこの画面は出ない | SC-A01 |

## 6. 使う API
| パス | いつ |
|------|------|
| GET `/api/admin/campaigns?status=pending` | 開いたとき・決めた後・409 の後。`status` は1つだけ（§11.7 の7つの許可リスト、配列は 400）。出力: 全店のキャンペーン（店・種類・名前・内容・特典・対象のスポットと季節・対象の人数（5人未満は数字なし）・期間・上限・重なりの数）。association だけ |
| GET `/api/admin/campaigns` | 記録の表のため（`status` なし）。確認の記録（日時・店・キャンペーン・結果・理由）を含む【仮定: 記録を同じ応答に入れる】 |
| POST `/api/admin/campaigns/:campaignId/review` | 確認のダイアログで決めたとき。`z.strictObject({ requestId, decision: 'approve'｜'reject', note?: 1〜100字 })`（仕様案 §8）。`reject` で `note` が無ければ 400【仮定】。`pending` でなければ 409。association だけ |

- 共通の決まり（`z.strictObject`・Origin 検査・`Content-Type`・`requestId`・`Cache-Control: no-store`・エラー形式）は `API設計.md` §1 と同じ。応答に利用者の ID を含めない（R-057）。

## 9. 試験で確かめる観点（仕様案 §9 から。合否は書かない）
- 権限: 店の役割では承認・差し戻しができない（404）。店の役割で GET `/api/admin/campaigns` が 404。`ADMIN_MODE` なしで 404。
- 自店だけ: どのキャンペーンも「使えるお店」が申請した店の1つだけで、盤から出たクーポンの `shop_id` が `campaigns.shop_id` と一致する（SC-A13 の 9 と同じ）。
- 承認前は盤に出ない。承認しても始まる日の前は盤に出ず、始まる日から出る（デモの時計で進める）。差し戻したものは盤に出ない。
- 入力: 未知キー・`decision` が許可リスト外・差し戻しで `note` なし・101字・`status` の配列の query が 400。`pending` でないものの review が 409。
- 二重送信: 同じ `requestId` で2回送っても、記録が1行だけで、結果が変わらない。
- 重なり: 同じスポット・重なる期間に実施中・承認済みが2つあるとき、3つ目の確認待ちに警告が出る。1つのときは出ない。
- 記録: 承認・差し戻し・店の途中停止が記録に残り、理由が文字のまま表示される（XSS の文字列が動かない）。
- 個人情報: 応答に `guest-` と CSV の7桁 ID が含まれない。対象の人数が5人未満なら数字が出ない。
- アクセシビリティ: 確認のダイアログでフォーカスが戻る、キーボードだけで承認・差し戻しができる、200% 拡大。

## 10. 【仮定】
- 確認待ちのカードは送られた古い順。メニューに確認待ちの件数を出す。
- 重なりの警告は、実施中に加えて承認済み（始まる前）も数える。警告があっても承認できる。
- 差し戻しの理由は必須（仕様案 §8 は `note?` だが §11.6 は「理由を付けて差し戻す」）。承認では送らない。改行は1つの空白にまとめる。
- 承認・差し戻しの前に確認のダイアログを出し、最初のフォーカスは［やめる］。決めた後は次のカードの見出しへフォーカスを移す。
- 承認の時点で始まる日を過ぎていたら 409（店に日を直してもらう）。
- 記録の表に「店が止めました」の行を出す（§11.6 の「店による途中停止」。15:45 にモックへ追加）。記録は GET `/api/admin/campaigns` の応答に入れる。
- 見え方のマスの番号は説明のための見本。
- この画面では上の帯の期間の選択を使わない。
