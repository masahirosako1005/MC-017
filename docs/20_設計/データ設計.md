作成: 2026-11-09 14:09（ファイルの更新時刻。当初の 14:26 は推測の誤りで訂正） / 到達点: M3（2.6） / 上流: `要件定義.md`（R-001・R-005・R-013〜R-033・R-028・R-056・R-057）、`データ調査.md`（CSV の列・件数・文字コード・整合性）。DDL の正は `db/schema.sql`（M4 で作成。本書と一致させる）。

## 1. 方針
- DB は SQLite（better-sqlite3）。本番相当はファイル（`DB_PATH`、既定 `data/app.db`）、試験と E2E は `:memory:`（environment ルール）。
- `PRAGMA foreign_keys = ON`。`NOT NULL`・`CHECK`・`UNIQUE`・外部キーで DB 側でも守る（R-056）。
- 日時は JST 固定。日付は `YYYY-MM-DD`、日時は `YYYY-MM-DDTHH:mm:ss+09:00`（ISO 8601）。「今日」はアプリ内の今日（ADR-008）。
- **個人に見える列（ユーザー名・メール・LINE ユーザ ID）と、使わない列（性別・居住地・職業）は取り込まない**（R-057）。
- 元の CSV は読むだけ。書き戻さない・複写しない（competition ルール）。

## 4. CSV 取込（R-028、ADR-009）
### 4.1 読み方
- `SAMPLE_DATA_DIR` のフォルダが無い・ファイルが無いときは「CSV のフォルダが見つかりません: SAMPLE_DATA_DIR を確かめてください」と出して終了。
- 先頭の BOM（EF BB BF）を外す。CRLF・LF の両方、引用符つきの値（`""` のエスケープ）を読める自前の読み取り（依存を足さない。データ調査 §1.1）。不正な UTF-8 は `TextDecoder('utf-8', { fatal: true })` で止める（SEC-IN-14）。
- 見出しの列名を確かめ、違えば取り込まずに理由を出す。各行は zod で検証し、合わない行は除外して理由ごとに数える。
- 1ファイル1トランザクション。`INSERT OR IGNORE`（一意キー）なので、**何度取り込んでも件数は増えない**（R-028、QL-DATA-02）。

### 4.2 取り込む列（ほかの列は読み捨て、DB に入れない）
| ファイル | 使う列 | 検証 | DB |
|----------|--------|------|----|
| `13_ユーザー一覧.csv` | ユーザーID・年代・登録日時 | ID は7桁の数字、年代は6区分、日時は `YYYY-MM-DD HH:MM:SS` | `csv_users` |
| `12_スタンプ獲得履歴.csv` | ユーザID・周回・スポット名・獲得日時 | ID が `csv_users` にある、周回 1〜9、スポット名が対応表にある、日時の形式 | `csv_stamps` |
| `18_特典獲得履歴.csv` | user_id・reward_name・timestamp | ID がある、名前 1〜40字、日時の形式 | `csv_rewards` |
| `08`・`09` | 使わない | — | — |
- 08（参加後アンケート）と 09（登録時アンケート）は、うわさ・予言に要る列が無いので取り込まない【仮定】（09 の年齢は 13 の年代と全員一致。データ調査 §1.2）。
- 検証のための突き合わせ（ログだけ）: 13 の「スタンプ獲得数」と 12 の件数、13 の「特典獲得数」と 18 の件数の不一致人数を数えて出す（データ調査では 0人・227人）。集計列は DB に入れない（データ調査 §3-3）。
- ログには件数と理由だけを出し、行の中身（名前・メール等）を出さない（SEC-ERR-09）。

### 4.3 CSV に無い値の付け方【仮定】
- 一緒に来た人: `['solo','family','couple','friends'][ユーザーID mod 4]`（決まった計算。毎回同じ）。
- 日付の並べ直し（うわさ）: CSV の20日間（10-01〜10-20）を、アプリ内の今日の前に繰り返し並べる。アプリ内の日付 d に対応する CSV の日は `10-01 + ((d − 2026-01-01 の日数) mod 20)`。「昨日」はアプリ内の昨日に対応する CSV の日、「過去1か月」は20日分すべて。

## 5. うわさの集計（R-027。SQL は repository、並べ方は service）
| 種類 | 集計 |
|------|------|
| 昨日の人気 | 対応する CSV の日のスタンプを、スポットごとに利用者の人数で数え、上位3つ |
| 過去1か月の人気 | 20日分の人数で上位3つ |
| 空いている時間帯 | 選んだスポット（既定は名古屋城 s1）の 9〜17時の時間ごとの件数。最大の半分未満を「空き」。0〜5時は営業時間外として数えない（データ調査 §2.2 の偏り） |
| 同じ年齢層に人気 | `csv_users.age` が自分と同じ人の人数で上位3つ |
| 同じ一緒に来た人に人気 | `csv_users.companion` が自分と同じ人の人数で上位3つ |
- 応答はスポット ID と人数だけ。利用者の ID は返さない（R-057）。

## 6. さいころの回数と盤の更新（R-005・R-013〜R-021・ADR-006・ADR-007）
1. 付与: 各きっかけで `grants` に1行（一意キーで1日1回）。付与の数: first 0（行を作らない）・day2 1・revisit 2・qr 1・note 1・invite 1・prophecy 2・demo 1〜10。
2. 振る: 1トランザクションで「残り回数 > 0 の確認 → `crypto.randomInt(1, 7)` → 位置を進める（44 で止める）→ `rolls` に1行 → 🎁ならクーポン → ゴールなら `board_no+1`・`pos=0`・ゴール特典」。途中で失敗したら全部戻る（R-056）。
3. 二重送信: `requests` に `requestId` と応答を同じトランザクションで保存し、2回目は保存した応答を返す。

## 7. 予言（R-030〜R-033。計算は ADR-010）
- 候補: `kind IN (sight, event)` で、自分の `stamps` に無いスポット。段差少なめの人は `step_free=1` だけ。
- 作る時: `GET /api/prophecy` で、open の予言が無く、`stamps` が1件以上のとき。
- 答え合わせ: 今日の `visits.kind='revisit'` かつ open の予言のスポットで QR を読んだとき（予言を作った日より後）。`status='visited'`・`visited_day`、`grants(source='prophecy', spot_key=予言のID)` で +2。
- 答え: `answer` が NULL か `later` のときだけ更新できる。`liked` で予言のスポットのタグの重み +0.5、`normal` で −0.5（範囲 −2〜3）。
- かしこさ: 答え合わせ（visited）の数で 0→1、1→2、3→3、5→4、8→5。的中率は liked ÷（liked＋normal）。

## 8. 個人情報とデータの範囲（R-057）
- 利用者が入れるのは、年齢の区分・一緒に来た人・段差少なめ・アバター・ひとこと（100字）だけ。ひとことには「名前や連絡先は書かないでね」と出す。
- DB の列に、名前・メール・LINE ID・性別・居住地・職業は無い（AC-066 で列名を全部確かめる）。

## 9. 運営向けの表（2026-11-10 追加。U-09〜U-12、`db/schema.sql`）
| 表・列 | 中身 | 決まり |
|--------|------|--------|
| `plans` | 次に行く予定（`user_id`・`spot_id`・`created_day`・`status` open｜done・`done_day`） | 同じ人・同じスポットの open は1つ（一意索引）。上限3は service。QR で `done` |
| `campaigns` | 店のキャンペーン（`request_id`（一意）・`shop_id`（s8・s9・s11 だけ）・`kind` item｜yen｜percent・`item_key`・`value`・`starts`・`ends`・`status` pending｜approved｜rejected・`created_day`・`reviewed_day`・`reject_reason`） | `kind` と `item_key`/`value` の組み合わせを CHECK。`ends >= starts`。名前は保存せず、`item_key`/`value` から作る |
| `board_extras` | 盤の 🏪（`user_id`・`board_no`・`campaign_id`・`square` 1〜43） | 主キー（人・盤・キャンペーン）、（人・盤・マス）も一意 |
| `coupons.campaign_id` | キャンペーンの券なら ID | `template_id` に `'campaign'` を足した。券の店は `campaigns.shop_id` |
| `notes.shop_visible` | 店に見せてよいか（0/1、既定 0） | 利用者アプリのひとこと画面の案内を変えたあとの書き込みだけ 1 |
| `note_reads` | 店が「確認した」声（`note_id`・`shop_id`） | 主キー（声・店）。取り消しなし |

- 古いファイル DB は `openDb` の移行で、`coupons`（許可に campaign が無い）を作り直して券を移し、`notes` に `shop_visible` を足す（試験 T-077）。
- 需要（近くの予定）は、店から 2.5km 以内の観光スポット・イベント（`sight`・`event`）の open の予定を持つ人の数（同じ人は1人）。
- 集計の定義は ADR-025。K-03 の盤の途中は1〜43マス（ゴール直後は0に戻る）。
