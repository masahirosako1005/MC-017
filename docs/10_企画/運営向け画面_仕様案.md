## 1. 目的
オーナー（観光協会・店舗）が次の2つに答えを出せる画面にする。

| 問い | 今の課題（事実） | 画面で見せるもの |
|------|------------------|------------------|
| **何に困っているか** | 要望 287件のうち約3割（95件）が移動の不安、26件が操作と特典の受け取り方、20件が周辺のお店の情報（`データ調査.md` §2.4） | 困りごとの分類・年代別・スポット別の件数と、その困りごとに効く打ち手 |
| **どうしたら再訪につながるか** | 満足度と2周目に関係が無い（大変満足 20/74、大変不満 4/16）。3日以上あけて戻った人は0人（同 §2.2・§2.4） | 「次に来る理由」を持って帰った人の割合と、その人たちが実際に再訪したか（再訪の因果をそのまま測る） |

- 満足度は再訪の先行指標にならないことが CSV で分かっているため、**主な指標は満足度ではなく「次に来る理由の保有」と「再訪」**にする。
- ダッシュボード（SC-A02）には、既存のスタンプラリーの基準値との比較を**出さない**（16:15 ユーザー指示）。既存の CSV は、困りごとの分類（SC-A04）とスポット別の件数（SC-A05）の材料にだけ使う。
- 管理サイトには「予言」に関する画面・指標・気づき・API・設定を**一切置かない**（16:17 ユーザー指示）。欠番: SC-A06・K-05・K-06・I-04・US-104・`GET /api/admin/prophecies`（番号は詰めない）。K-03 の②は「予言」ではなく、利用者が入れた「次に行く予定」（open）で数える【仮定】。予言そのものは利用者アプリの機能として残る。

## 2. 利用者と権限【仮定】
| 役割 | 見られる範囲 | 変えられるもの |
|------|-------------|---------------|
| 観光協会（association） | 全スポット・全店舗の集計、困りごと、取込の状態 | 盤・クーポンの型・再訪ボーナスの設定、スポットの公開、施策の記録 |
| 店舗（shop: s8 あかり堂 / s9 きしめん ひだまり / s11 みそかつ こもれび） | **自店のクーポンと自店の QR だけ**＋エリア全体の合計（他店の個別の数字は見せない） | 自店のクーポンの一時停止・1日の上限 |

- 競技ルールでログインは作らない。【仮定】`ADMIN_MODE=1` のときだけ `/admin` と `/api/admin/*` を登録し（DEMO_MODE と同じ扱い、ADR-008）、最初の画面で役割を選ぶ。役割はヘッダ `X-Operator: association | shop-s8 | shop-s9 | shop-s11` で送り、サーバーで zod 検証する。127.0.0.1 だけで動くため成りすましの危険は限られるが、本番運用では認証が要る旨を画面と設計書に書く。
- 画面は PC（1280px）と、レジ横のタブレット（768px）を想定。利用者アプリのスマホ幅は対象外【仮定】。

## 4. 指標の定義
「今日」はアプリ内の今日（ADR-008）。期間は画面で選ぶ（既定は直近28日【仮定】）。

| ID | 指標 | 定義 | 見る理由 |
|----|------|------|---------|
| K-01 | 利用者数 | 期間内に `visits` が1行以上ある利用者 | 母数 |
| K-02 | **再訪率** | 期間内に `visits.kind='revisit'`（前回から7日以上あいた日）がある利用者 ÷ K-01 | 最終の成果。旅の2日目（`day2`）は数えない（C1） |
| K-03 | **次の理由の保有率** | その日の終わりに、①盤が途中（1〜48マス）②open の「次に行く予定」③「次に来た日から」のクーポン（`usable_from` が翌日以降）の**どれかを持って帰った**利用者 ÷ その日の利用者 | 再訪の因果の「気持ち」の段。帰る時点で理由が残ったか |
| K-04 | 理由別の再訪率 | K-03 の①②③それぞれを持って帰った人の、その後の再訪率。持たずに帰った人と並べる | どの理由が効いているか |
| K-07 | 次回クーポンの利用率 | `season`・`goal` のうち `used_at` がある数 ÷ 発行数。期限切れ率も並べる | 「使いに来る」が起きたか |
| K-08 | きっかけの内訳 | `grants.source` 別（qr・note・invite・day2・revisit）の件数 | どの行動が多いか |
| K-09 | 盤の止まり位置 | 再訪しなかった人の最後の `pos` の分布 | どこで飽きたか（🎁の間隔の見直し） |
| K-10 | 困りごと件数 | 08 の要望を分類した件数（年代別） | 何に困っているか |
| K-11 | 店の特典マスの効果 | キャンペーンごとの対象人数・置いたマス・止まった人・配った枚数・使った枚数・再訪の日に使った割合（§11.7） | 店の先回りが来店につながったか |
- **段ごとの数え方**【仮定】: SC-A03 の段は「前の段も通った人」だけを数える。理由を持たずに再訪した人は段の外に別に書く（15:40 追加）。
- **小さい数は隠す**【仮定】: 集計のマスが5人未満なら「5人未満」と出す（個人が推測されないため）。時間帯×曜日の件数も同じ。5人未満のマスを含む合計は「n人以上」と出し、差し引きで人数が分からないようにする（15:40 追加）。30人未満の比較は「参考」と灰色で出し、関係を因果と言い切らない（K-04 は「持って帰った人ほど再訪している」という関係で、原因とは書かない）。
- 応答に利用者の ID（`guest-xxxxxx`・CSV の ID）を一切含めない（R-057）。

### 5.1 画面の約束（共通）
- グラフは自前の SVG か CSS の棒にする（グラフの OSS は入れない。入れるなら 
pm view` と外部リソース.md が先）。**グラフと同じ内容の表を必ず並べる**（WCAG 1.1.1）。色だけで差を示さず、数値と記号（▲▼）を付ける（1.4.1）。
- 絞り込み（期間・年代・一緒に来た人）はキーボードで操作でき、ボタンは 44px 以上。200% に拡大しても横に流れない（1.4.10）。

- 日本語のみ【仮定】（利用者アプリは英語あり。運営画面は地元の運営者が使うため）。
- 地図は出さない【仮定】。出す場合は利用者アプリと同じく「出典：地理院タイル」とオフライン表示の決まりに従う。

## 6. 気づきと打ち手（LLM なし・決まった規則）
### 6.1 気づき（SC-A02 に上位3件）
規則で判定し、根拠の数字を必ず添える。同じデータなら同じ結果。

| ID | 条件 | 出す文（例） |
|----|------|-------------|
| I-01 | K-03 が前の期間より5ポイント以上下がった | 「帰るときに次の理由を持っている人が減っています（62%→55%）」 |
| I-02 | K-04 で、ある理由を持った人の再訪率が持たない人の2倍以上（各30人以上） | 「次回クーポンを持って帰った人は、持たない人の2.3倍戻っています」 |
| I-03 | 店の次回クーポンの期限切れ率が50%以上 | 「あかり堂の季節の1品は、6割が使われずに期限切れです」 |
| I-05 | K-09 で同じ区間に止まる人が全体の20%以上 | 「1枚目の20〜28マスで止まる人が多いです」 |
| I-06 | 困りごとの1分類が全体の25%以上 | 「移動の不安が最も多い困りごとです（95件）」 |

### 6.2 困りごと → 打ち手（SC-A04）
既に利用者アプリにある仕組みに結びつける。打ち手を選ぶと SC-A09 に施策として記録できる。

| 困りごと（08 の分類） | 打ち手の候補 | 効いたかを見る指標 |
|----------------------|-------------|-------------------|
| 移動の不安（95） | 段差少なめのコースを増やす、休憩所の数をコースに出す（C2） | 段差少なめ利用者の K-02 |
| 操作と特典の受け取り方（26） | クーポンに使い方・お店・期限を明記、初回の案内（C4） | K-07、クーポンの「使う」までの日数 |
| 周辺のお店の情報（20） | スポット詳細の「近くのお店」を増やす（C3） | 店舗の QR 数、同じ日の寄り道 |
| 特典・景品の魅力（19） | 季節の1品の中身を替える（C5） | K-07 |
| スタンプ収集が単調（11） | 2枚目の盤の季節マスを替える（C8） | K-09 |
| スポットの説明（10） | 架空のスポットの説明を厚くする | 該当スポットの QR 数 |
| 混雑（5） | うわさの「空いている時間帯」を目立たせる | 時間帯の偏り |

## 9. 試験の観点（追加分）
- 指標の計算: 決まった小さいデータで K-02・K-03・K-04 の値が手計算と一致する（day2 を再訪に数えない、境界の7日ちょうど）。
- 権限: 店舗の役割で他店の `shopId` を指定すると 404、観光協会の API は 403 か 404。`ADMIN_MODE` なしでは `/admin` も `/api/admin/*` も 404。
- 個人情報: 全応答に `guest-` と CSV の7桁 ID が含まれない。5人未満のマスが数字で出ない。ひとことの本文が応答に含まれない。
- 入力: 期間の逆転・367日以上・未知キー・配列の query・XSS と SQLi の文字列（施策の本文）が 400 か、安全に表示される。
- 設定の変更: 適用日より前のクーポンは変わらない。二重送信で履歴が2行にならない。
- 書き出し: `=` で始まる値が数式にならない。
- アクセシビリティ: グラフに同じ内容の表がある、キーボードだけで絞り込める、200% 拡大。
- 店の特典マス（§11）:
  - 作れる条件: 対象が閾値ちょうど（10人）で作れ、9人では 409。2.5km の外のスポットを対象にすると 400。
  - 自店だけ（15:58 追加）: 作る本文に `shopId`・`shopIds`・`usableShops` を入れると 400。URL の店が自分と違うと 404。ほかの店の店名を名前・内容・品名に入れると 400。できたクーポンの「使えるお店」が自店の1つだけで、盤から出たクーポンの `shop_id` が `campaigns.shop_id` と一致する。「使える」を押せるのは、そのクーポンの店のページだけ（SC-07 の表示も自店のみ）。
  - 特典の例（15:58）: 「コーヒー1杯」の無料、100円引き、「アイス」のサービスが作れて、旅行者の画面に「コーヒー1杯 無料」「100円引き」「アイス サービス」と出る。
  - 置く場所: 同じ利用者・同じキャンペーンなら毎回同じマス。🎁・スポット・季節・ゴール・ほかの店のマスを置き換えない。いまの位置より後ろに置かない。1枚の盤に4つ目を置かない。
  - 配る枚数: 上限ちょうどで次の人は「配布は終わりました」。同時に止まっても上限を超えない（トランザクション）。同じ人に2枚目が出ない。
  - 使える日: 手に入れた当日と期限の翌日は 409、翌日から期限の日までは使える。
  - 文字: URL・メール・電話番号の形は 400。XSS の文字列は文字のまま表示される。
  - 権限: 他店のキャンペーンの操作は 404。店の役割では承認できない。承認前は盤に出ない。
  - 予定: open は3件まで。取り消すと対象から外れ、まだ置いていないマスは置かない。店への応答に利用者 ID が無く、5人未満のマスは隠れる。
  - アクセシビリティ: 店のマスは色だけでなく 🏪 と店名の文字で分かり、盤の文字の説明に「次のお店の特典まで n マス」が出る。

## 10. 規模と進め方【仮定】
- 目安: Must（SC-A01・A02・A03・A04・A10 と 08 の取込）で約1.5時間、Should を全部で約1.5時間。§11 の店の特典マスは、利用者アプリ側（予定・盤のマス）と運営側を合わせて約1.5時間【仮定】。
- 利用者アプリの Must（U-02〜U-08、約2.5時間）が残っているため、**利用者アプリの Must を先に終え、そのあと運営画面の Must を新しいユニット（U-09 運営の分析、U-10 店舗）として足す**のが安全。要件定義・画面モック・画面設計・追跡表・試験項目へ入れるのは、この案で進めると決まってから。

## 11. 近くの「次回訪問予定」に合わせた店の特典マス（15:23 追加）
### 11.1 流れと再訪の因果
```
旅行者: 予言・スポットを「次に行く予定」に入れる
   ▼
店舗: 近くのスポットの予定の人数が多い → イベント・クーポンを作る → 観光協会が確認
   ▼
予定がある人の盤の少し先に「お店の特典マス」🏪 が現れる
   ▼
止まると、翌日から使えるクーポン → 次の旅で、予定のスポットのついでに店へ寄る
```
- 旅行者の側: 盤の先に店のマスが見える（体験）→「止まりたい・次の旅で使いたい」（気持ち）→ 予定の日に店にも寄る（次に来る理由）。
- 店の側: 予定は「これから来る客」の先読みなので、来る前に手を打てる。終わった後の集計（§1〜§10）と違い、**先の需要に合わせて動ける**のがこの機能の価値。

### 11.2 利用者アプリに足すもの
今の利用者アプリには「次回訪問予定」を登録する仕組みが無い（予言は自動で1つ出るだけ）。そのため次を足す【仮定】。

| 画面 | 追加 |
|------|------|
| SC-09 予言と答え合わせ | 予言カードに「次に行く予定に入れる」。予言のスポット・季節・時間帯をそのまま予定にする |
| SC-04 スポット詳細 | 同じボタン。季節を選ぶ（既定は次の季節）。sight・event のスポットだけ（店は予定にしない） |
| 予定の一覧（SC-09 の中） | open の予定は1人3件まで。取り消せる。予定のスポットで再訪の日に QR を読むと「行った」になる。予言の答え合わせ（R-031）は今のまま |
| SC-05 すごろく | 新しいマスの種類「お店の特典マス」。🎁とは別の色に加えて 🏪 と店名の文字で区別する（色だけに頼らない）。盤の文字の説明に「次のお店の特典まで n マス」 |
| SC-01 ホーム | 店のマスが置かれた日に1回だけ「近くのお店から特典マスが届きました」 |

### 11.3 店舗が見るもの（SC-A13 の上半分）
- **近くのスポット**: 店の位置から直線 2.5km 以内のスポット【仮定】。マスタの概略座標（`データ設計.md` §2.1）で計算した値（15:23 実測）は次のとおり。

| 店 | 近くのスポット（距離） |
|----|------------------------|
| s8 あかり堂 | s7 名古屋市科学館 1.52km、s10 大須 冬あかり横丁 2.08km、s1 名古屋城 2.21km |
| s9 きしめん ひだまり | s7 0.66km、s10 1.07km、s2 鶴舞公園 1.80km、s1 1.92km |
| s11 みそかつ こもれび | s10 0.69km、s2 0.91km、s7 1.00km |

- 表: 近くのスポットごとの open の予定人数、予定の季節・時間帯別、年代・一緒に来た人の内訳、前の週との差。**5人未満のマスは「5人未満」**。利用者 ID は返さない。
- **「多い」の判定**【仮定】: 対象にできる人（選んだスポット・季節に open の予定がある人）が **10人以上**のとき「作れます」にする。足りないときは「あと n 人で作れます」と出し、作成ボタンは押せない（5人未満のときは n も「5人以上」とだけ出す）。閾値は観光協会が SC-A07 で 5〜100 の範囲で変えられる。

### 11.4 イベント・クーポンの作り方（SC-A13 の下半分）
| 項目 | 決まり |
|------|--------|
| 種類 | クーポン / イベント（イベントは「参加でもらえる特典」のクーポンつき） |
| **使えるお店（15:58 追加）** | **自分の店だけ。選べず、画面には「使えるお店: あかり堂（自分の店だけ）」と文字で出す**。ほかの店・ほかのスポットで使えるクーポン、店をまたぐクーポンは作れない |
| 対象のスポット | 近くのスポットから1つ以上。これは「**だれの盤に出すか**（そのスポットに予定がある人）」を決めるもので、クーポンを使える場所ではない |
| 対象の季節 | 予定の季節から1つ（既定は最も多い季節） |
| 名前・内容 | 名前 1〜20字、内容 1〜60字。改行なし。URL・メール・電話番号の形は受け付けない（外へ誘導しない・連絡先を出さない）。**ほかの店の店名（マスタの店名）を含む文も受け付けない**【仮定: NFKC・空白を除いて比べる】 |
| イベントの日時 | 日付1つと、9〜21時の中の決まった時間の枠から1つ（15:40 に「開始と終了の時刻」から変更）。場所は店 |
| 特典（自店で渡せるものだけ） | 次の3つのどれか1つ。**①1品を無料・サービス**（品名 1〜20字。例: コーヒー1杯、アイス）／**②○円引き**（50〜1,000円。例: 100円引き）／**③○%引き**（5〜50%）。旅行者には「コーヒー1杯 無料」「100円引き」「アイス サービス」のように、品名か金額を店名とあわせて出す（15:58 に表示名と例を追加） |
| 期間 | 開始は翌日以降、長さ 7〜90日 |
| 配る枚数 | 上限 1〜500枚、1人1枚 |
| 同時に出せる数 | 1店あたり、確認待ちと実施中を合わせて2つまで |

- 送る前に、盤のマスとクーポンの見た目をプレビューで出す。送ると「確認待ち」になる。
- **自店のクーポンだけにする守り方**（15:58 追加。画面だけでなくサーバーで守る）:
  1. 店は URL の `:shopId` と役割（`X-Operator: shop-sX`）が同じときだけ作れる（違えば 404）。
  2. 本文に店・「使えるお店」の項目を持たせない（`z.strictObject` で、`shopId`・`shopIds`・`usableShops` などは未知キーとして 400）。
  3. 作るクーポンの店 `shop_id` は、必ず URL の店（`campaigns.shop_id`）から決める。盤のマスから出すクーポンも `campaigns.shop_id` をそのまま使う。
  4. 名前・内容・品名にほかの店の店名があれば 400。
  5. 観光協会は確認のとき「使えるお店」が店の1つだけであることを見る（SC-A14）。

### 11.5 盤への置き方（決まった計算）
- **対象者**: 実施中に、対象のスポットに対象の季節の open の予定がある人。実施中に新しく予定を入れた人も、その日の最初の `POST /api/session` で対象になる。
- **置く場所**: いまの盤で、いまの位置の3〜10マス先にある「ふつうのマス」（🎁・スポット・季節・ゴール・ほかの店のマスではないマス）のうち、`(利用者 ID とキャンペーン ID から作る数) mod 候補の数` 番目。候補が無ければ次の盤のはじめの方に同じ計算で置く【仮定】。
- 1枚の盤に店のマスは3つまで。今の🎁マスを消さない・置き換えない（盤の約束と既存の試験 AC-026 を壊さない）。
- 置いたマスは `board_extras` に保存し、後から動かさない（盤が日によって変わらない）。ゴールして次の盤になったら、止まらなかった店のマスは消える【仮定】。
- **止まったとき**: 振る処理と同じトランザクションで「配った枚数 < 上限」を確かめてクーポンを1枚出す（`UNIQUE(user_id, campaign_id)`）。上限に達していたら「配布は終わりました」と出してふつうのマスとして扱う。期間が終わったマスは「終了」と出し、止まっても何も出ない。通り過ぎただけでは出ない（🎁と同じ、R-019）。
- **使える日**: 手に入れた翌日からキャンペーンの最終日まで【仮定】。当日すぐ使えないのは、予定の旅で寄ってもらうため。ほかのクーポンの7日（R-026）にしないのは、期間が7日のキャンペーンでも使えるようにするため。

### 11.6 観光協会の確認（SC-A14）
- 確認待ちの一覧と、盤のマス・クーポンのプレビュー。承認するか、理由（1〜100字）を付けて差し戻す。
- 同じスポット・重なる期間に実施中のキャンペーンが3つ以上になるときは警告を出す（盤が店のマスばかりにならないため）。
- 承認・差し戻し・店による途中停止は、変更履歴（`settings_history` と同じ形）に残す。
- 確認を入れる理由: 店が書いた文が旅行者全員の盤に出るため。誤解を招く表現や連絡先を出させない。

### 11.7 状態と効果
- 状態: `draft → pending →（承認）approved →（開始日）active → ended`。ほかに `rejected`（差し戻し）と `stopped`（店が途中で止めた。新しく置かず、置いたマスは「終了」）。
- 効果（K-11、SC-A10 と SC-A13）: キャンペーンごとに、対象の人数、置いたマス、止まった人、配った枚数、使った枚数、使った日が再訪の日だった割合、対象者の予定スポットへの再訪率。再訪率は、同じスポットに予定があって対象外だった人と並べる（30人未満は「参考」で、因果とは書かない）。

### 11.9 デモ【仮定】
- DEMO_MODE のときだけ、ダミーの予定を CSV の利用者から決まった計算で足し、閾値を超えた状態を SC-A13 で見せられるようにする。画面に「ダミーを含む」と出す。ダミーの利用者には盤が無いので、盤のマスはデモの利用者が自分で予定を入れて確かめる。
- 通しのデモ: 利用者がスポットを予定に入れる → 店がキャンペーンを作る → 観光協会が承認 → デモの時計で開始日へ進める → 盤に 🏪 → 止まる → 翌日へ進めてクーポンを使う。

### 11.10 焼き直しにしない点
既存アプリの特典は「スタンプを集めた後の景品」で、旅の中で完結する。この機能は、**旅行者の次回の予定に、店が来る前から応える**仕組みで、特典は次の旅で使う形になっている。クーポンは土台として使うだけで、中心は「予定 → 店の先回り → 次の旅で寄る」のつながり。
