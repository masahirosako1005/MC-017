## 1. 意図

観光客が名古屋の街で**すごろく**を進める。さいころは「行く（QR）・買う（レジ横の QR）・書く（ひとこと）・誘う（友達へ LINE モック）」で振れる。すごろくは1回の旅では終わらず、**次に来た日に続きから再開**でき、再訪した日にもさいころを振れる。ゴールすると**特典マスが増えた2枚目**が出る。

- ねらい（ユーザー指示）: **買い物・ひとこと・友達への誘い（口コミ）を増やす**。
- 再訪の理由: 「すごろくの続き」「再訪ボーナスのさいころ」「2枚目の特典マス」「友達と行く約束」「季節のイベント」「次回のおすすめコース」「うわさで見つけた人気スポット」。

## 2. 既存機能との関係（焼き直しにしない）

既存のスタンプラリー機能は**土台としてだけ**使い、中核は新しい仕組みに置く（competition ルール）。

| 既存機能 | 本企画での扱い |
|----------|----------------|
| 地図 | 土台。スポットと季節のイベントを探す入口 |
| QR スタンプ | 土台。さいころを振る3つのきっかけの1つ（スタンプを集めること自体は目的にしない）。読み取りはモックのボタン |
| 特典クーポン | 土台。すごろくの**特典マス**で手に入る（スタンプ数の交換ではない） |

| 音声案内 | 使わない。アバターの「声」は案内ではなく吹き出しの読み上げ（§5）【仮定】 |

新しい中核: すごろくの途中再開・再訪ボーナス・2枚目、ひとこと、友達を誘う、自分宛リマインド、次回のおすすめコース、うわさ。

| 項目 | 内容 |
|------|------|
| 舞台 | 名古屋市 |
| 架空（ダミー） | 観光地・飲食店・お土産屋・イベント |
| 実在の位置を使う種別 | 動物園・水族館・博物館・科学館・競技場・テーマパーク・大きな公園、と**名古屋城**（2026-11-09 11:41 ユーザー指示で追加）**のみ** |
| CSV | 利用者・スタンプ履歴を、上記のダミースポットに対応付ける（対応付けの方法は M2 の CSV データ調査で決める） |
| うわさ用の行動データ | ダミーで作る |

【仮定】
- 実在施設は**名称と位置だけ**使い、説明文・営業時間・料金は書かない（誤った案内を防ぐ）。実在施設で開くイベントも架空。画面に「スポットの内容とイベントは架空です（一部の施設は位置のみ実在）」と出す。
- 実在施設の座標は**開発時に**公開情報（地理院地図など）で確かめ、出典を `外部リソース.md` に書く。アプリの実行時には外部から取らない。施設の候補は M3 で確定。
- 名古屋城は実在の位置を使うスポットとする（ユーザー指示）。ほかの実在施設と同じく、名称と位置だけを使い、説明文・営業時間・料金は書かない。名古屋城で開くイベントも架空。アバターの「城」（とうじい）と「お堀」（ぴっこん）は、名古屋城をモチーフにする。
- 元 CSV は読み取り専用のまま。対応表とダミーの行動データは別に作り、CSV へ書き戻さない・複写しない。ダミーの行動データは固定の乱数の種で作り、毎回同じ結果になるようにする（試験の再現のため）。
- 個人に見える列（名前・LINE ID 等）は画面に出さない。うわさは集計値だけ見せる。

## 4. 利用者と設定

- ログインなし。**この端末の利用者は1人**として扱う。ダミー ID（`guest-xxxxxx`）を端末内で作る。
- ホームに**「はじめに選んでね」**: ① 年齢（10歳刻みのプルダウン）→ ② 一緒に来た人（ひとり・家族・夫婦・友達のプルダウン）の順に選ぶ。
  - 年齢の選択肢は CSV の年代に合わせて「10代・20代・30代・40代・50代・60代以上」の6区分（`データ調査.md` §2.1。2026-11-09 11:44 更新）。
  - 【仮定】選ばなくても使える（選ぶと、うわさの「同じ年齢層」「同じ一緒に来た人」とおすすめが出る）。あとからホームで変えられる。
- **別の日に開いたら再訪**。デモでは日付を切り替える。ただし、連続した日は「旅の2日目」として再訪と分ける（C1、§13）。
  - 【仮定】「デモ：日付を進める」操作は、アプリ内の「今日」だけを変える（端末の時計は変えない）。1日1回の判定も、このアプリ内の「今日」で行う。
- **文字サイズ切り替え**（【仮定】標準・大・特大の3段）と**日本語/英語**の切り替え。
- 多様な旅行者への対応: 年齢・一緒に来た人でうわさとおすすめを変える、文字サイズ、英語。

## 6. 画面

下のメニュー: **ホーム・スポット・遊ぶ・うわさ・特典**。

### ホーム
- 遊び方。
- いま選んでいるアバター（絵と名前）と、その横に「変更」リンク（→ アバター選択画面）。
- 「はじめに選んでね」（年齢 → 一緒に来た人）。
- 目的（観光地巡り・グルメ・ゆっくり散策など）を選ぶと、**おすすめコースを複数**出す。各コースに所要時間・歩く距離・段差の少なさ・休憩所の数を出し、「ゆっくり・段差少なめ」も選べる（C2）。
- 注目のイベント。
- このアプリでの行動の履歴。

### スポット
- 名古屋の地図にスポットのアイコン。押すと**下から1/3の高さ**で概要、「詳細」で全画面。
- 地図に季節のイベントを**春夏秋冬のタブ**で出す。**通年のイベントは全タブに出す**。
- 詳細:
  - **QR スタンプ**（読み取りはモックのボタン）。取れたら「すごろくで遊ぶ」ボタン。
  - **友達を誘う**: 「今度ここに一緒に行こうね」の LINE 画面（モック。送らない）。送信（モック）を押すとさいころを1回振れる。
  - **ひとこと**: 感想の欄（100字まで）。「書くとすごろくを1回振れる」と書き、送信するとすごろくが起動する。
  - **近くのお店**: レジ横 QR のあるお土産屋・飲食店を、そのスポットから近い順に出す（C3）。
  - **みんなのひとこと**: ほかの旅行者のひとこと（ダミーだけ）を年代・一緒に来た人つきで読める。自分のひとことはほかの人に見せない（C6）。
- 【仮定】地図と同じ内容を**一覧**でも見られるようにする（WCAG 2.2 のドラッグ動作の代替・地図を見づらい人向け。security-quality ルール）。
- 【仮定】概要の下からの表示が出ていても「出典：地理院タイル」が隠れない位置に置く（地図が見える画面では常時表示）。

### 遊ぶ（すごろく）
- 【仮定】指示の見出し「■選ぶ」は、下のメニューの「遊ぶ」（すごろく）のことと読んだ。
- 再訪すると途中から再開できる。ゴールすると2枚目が出て特典マスが増える。
- 2枚目は1枚目と同じ道をなぞらず、別のエリアや季節のマスを入れる（C8。既存アプリの「2周目」と違いを出す）。

### うわさ
- 昨日の人気スポット、過去1か月の人気スポット、空いている時間帯、同じ年齢層に人気のスポット、同じ一緒に来た人に人気のスポット。
- 【仮定】「昨日」「過去1か月」はアプリ内の「今日」（デモの日付切り替え後も含む）を基準にする。

### 特典
- 特典はクーポン。取ったスタンプと特典の一覧と、利用済みかどうか。
- お店で「使う」を押すと利用済み。【仮定】取り消せない操作なので、押した後に確認を1回はさむ。
- クーポンごとに使い方・使えるお店・期限を書く（C4）。
- 特典マスの一部は「次に来た日から使えるクーポン」で、季節で中身が変わる（C5）。

### その他の画面
アバター選択画面、スポット詳細（全画面）、LINE モック画面。画面 ID（SC-xx）は M3 で振る。

## 7. さいころとすごろくのきまり

| さいころを振れるきっかけ | 条件 | 上限 |
|--------------------------|------|------|
| 再訪 | 前回の旅から一定の日数（【仮定】7日）以上あけて開いた（C1） | 1日1回 |
| 旅の2日目 | 前回から7日未満の別の日に開いた（C1） | 【仮定】1日1回。中身は「再訪」より小さいボーナス（M3 で決める） |
| QR スタンプ | 観光スポットの QR、またはお土産屋・飲食店のレジ横の QR（買い物すると読める）をモックのボタンで読む | 1スポット1日1回 |
| ひとこと | スポット詳細で感想（100字まで）を送信 | 1スポット1日1回 |
| 友達を誘う | LINE モックで送信を押す | 1スポット1日1回 |

【仮定】
- 「1スポット1日1回」は**きっかけごと**に数える（同じスポット・同じ日に QR・ひとこと・誘うで最大3回）。「3つ合わせて1回」とも読めるので、M3 の要件定義で確定する。
- 最初に使った日は「再訪」にも「旅の2日目」にも数えない。その日に初めて開いたときに、前回からあいた日数で「再訪」か「旅の2日目」かを決める。
- 振れる回数は保存しておき、その場ですごろくを開く。あとで「遊ぶ」から振ってもよく、日をまたいでも消えない。
- さいころの目と回数の上限は**サーバー側で決めて記録する**（画面の操作だけで回数や目を増やせないようにする。データ完全性）。
- 盤のマス数・マスの種類は §16（2026-11-09 12:55 ユーザー指示）で決めた。50マス、5マスに1つ程度が🎁マス。**【2026-11-09 17:04 に変更】人の判断「これをアプリに取り込んで」で、盤は45マス・左上スタート／右下ゴール・名古屋城・特典は1/5・さいころは画面いっぱいの約4.8秒になった（ADR-022）。以降の「50マス」「下がスタート」「約3秒」はこの変更前の記述。**

## 8. LINE（モック）

- 友達を誘う: 「今度ここに一緒に行こうね」の文面を見せ、送信（モック）を押しても**どこにも送らない**。【仮定】画面に「見本です。実際には送信されません」と出す。
- 自分宛に季節のイベントをリマインド（モック）。【仮定】アプリ内の「お知らせ」に入り、デモで日付を進めると表示される。
- リマインドするのは自分で選んだイベントだけで、頻度も選べる（C7）。
- LINE ID などは扱わない。外部通信なし。

## 9. 再訪の因果（体験 → 気持ち → 次に来る理由）

| 仕組み | 体験 | 気持ち | 次に来る理由 | 増やしたい行動 |
|--------|------|--------|--------------|----------------|
| すごろくの途中再開 | 旅の終わりに駒が盤の途中で止まる | 続きが気になる | 続きをしに来る | 再訪 |
| 再訪ボーナスのさいころ | 別の日に開くとすぐ1回振れる | 来ただけで進めて得した | 来れば必ず進む | 再訪 |
| 2枚目のすごろく | ゴールすると特典マスの多い盤が出る | もっと得したい | 2枚目の特典を取りに来る | 再訪・買い物 |
| レジ横の QR | 買い物するとさいころが振れる | ついでに買おう | 進めたいときに店へ寄る | 買い物 |
| ひとこと | 感想を書くと振れる | 思い出を残せた | 書いた場所を見返し、また行きたくなる | ひとこと |
| 友達を誘う | 「今度一緒に行こうね」を送る（モック） | 約束した | 友達と一緒に来る | 口コミ・再訪 |
| 季節のイベントのリマインド | 自分宛に季節のイベントを残す（モック） | 次の季節が楽しみ | 次の季節のイベントに来る | 再訪 |
| 次回のおすすめコース | 次に回るコースが出る | 次の旅の予定が立つ | 計画どおりに来る | 再訪 |
| うわさ | 同じ年齢層・同じ同行者の人気、空いている時間帯が見える | 自分向けの場所が見つかった | 気になった場所へ行く | 再訪・回遊 |
| 特典クーポン | 特典マスでクーポンが取れる | 使いたい | 使いに店へ行く | 買い物・再訪 |

### 気づいた弱点（M2 の採点と補強案の材料。現時点の気づきで【仮定】）
1. 遠くから来る観光客の再訪は数か月〜年単位になりうる。「別の日に開いたら再訪」だけでは、間が空いた後に戻ってくる気持ちが弱まる。→ C1（旅の2日目と分ける）と C5（次に来た日から使えるクーポン）で一部を補う。
2. 1回の旅でさいころを振れる回数が多いと、その日のうちにゴールして「続き」が残らない。盤の長さと回数のつり合いが要る。CSV では1泊2日の旅が多い（`データ調査.md` §2.2）ので、2日分の回数で考える。
3. 2枚目のゴール後に、次に来る理由が残るかが決まっていない。→ C8（2枚目は盤を変える）は2枚目までの話で、ゴール後は未解決。
4. ログインなしで端末内だけのため、端末を替えると続きが消える。
5. うわさの元データがダミーのため、「人気」の説得力は見せ方に頼る。

## 10. デモの筋書き

**初回の旅 → 日付を進めて再訪 → すごろく再開 → ゴール → 2枚目**を通しで見せる。

1. 初回: ホームで「はじめに選んでね」（年齢・一緒に来た人）→ アバター（ともにゃん）→ 目的を選んでおすすめコース → スポットの地図 → 概要 → 詳細 → QR（モック）→ すごろくで遊ぶ → ひとこと → 友達を誘う（モック）→ 盤の途中で終わる。
2. 「デモ：日付を進める」で1日進める → 「旅の2日目」と判定。さらに7日以上進める → 再訪と判定 → 再訪ボーナスのさいころと、前回取った「次に来た日から使えるクーポン」が使えるようになる。
3. すごろくを途中から再開 → ゴール → 2枚目（特典マスが増える）→ 特典で「使う」→ 利用済み。
4. 途中で、うわさ（昨日・過去1か月・空いている時間帯・同じ年齢層・同じ同行者）とリマインドを見せる。

| ほしろう | 70 | 満別花丸（元気） |
| ぴっこん | 54 | 春歌ナナ |
| とうじい | 42 | ちび式じい |

- **音声は保存しない**（ファイルにも DB にも残さない）。
- **起動時に短い文で一度温める**。【仮定】温めに失敗してもサーバーは止めず、ログに1行残して、`/api/tts` は 503 を返す状態で動く。
- 【仮定】`/api/tts` の応答は `Content-Type: audio/wav`・`Cache-Control: no-store`。エンジンの呼び出しには時間の上限をつける（例 10秒）。エラー応答にエンジンの中身を出さない。
- 【仮定】§5 の「ともにゃんは少し早口」は、`audio_query` の話す速さを少し上げて表す。

### 17.2 代わり
- **エンジンが止まっていれば `/api/tts` は 503 を返し**、画面は**ブラウザの読み上げ**（Web Speech API の `speechSynthesis`）に戻す。
- 使うのは**端末内の声だけ**（`localService` が真のもの）。**日本語の Nanami があれば優先**し、**名前に Online がつく声は使わない**。
- 【仮定】Nanami が無ければ、ほかの端末内の日本語の声を使う。英語表示のときは端末内の英語の声を使う。どれも無ければ吹き出しの文字だけにする。
- 【仮定】503 を受けたら、その画面を開いている間はブラウザの読み上げを使い続ける（毎回サーバーに問い合わせない）。次に画面を開いたときにもう一度 VOICEVOX を試す。

### 17.3 見せ方
- **設定に、いま使っている声の名前を出す**（例「VOICEVOX:春日部つむぎ」、ブラウザの読み上げなら端末の声の名前）。
- **VOICEVOX の声のときは**、次の2か所に **「VOICEVOX:話者名」を常に表示**する。
  1. 声が出る画面の隅
  2. 設定の「ライセンスと出典」
- 同じ2か所に **VOICEVOX ENGINE**（LGPLv3）と、**配布元の名前と URL** も載せる。【仮定】配布元は VOICEVOX ENGINE のリポジトリ（https://github.com/VOICEVOX/voicevox_engine）の見込み。M4 で `音声合成の準備.md` と配布元のページで確かめてから書く。
- **`音声合成の準備.md` に「表示が必要」と書かれた文言は、その通りに出す**。各キャラクターの利用規約で求められる表記もその文書に従う【仮定】。
- **CSP は `media-src blob:` だけ足す**（WAV を Blob にして `<audio>` で鳴らすため）。ほかの指定は変えない。
- **再生中だけ口を動かす**: 表情の絵と talk の絵を **0.15秒ほどで交互**に出す。【仮定】動きを減らす設定では交互にせず、再生中は talk の絵のままにする。
- **すごろくの応援・クーポン・ゴールのセリフも、吹き出しと同時に読み上げる**。【仮定】さいころを押すなど利用者の操作のあとだけ読み、画面を開いただけでは読まない。前のセリフがまだ鳴っていたら止めて、新しいセリフを読む。
- **音の ON/OFF（§16.5）で止められる**。OFF にした瞬間に再生中の声も止める。【仮定】スクリーンリーダーへの結果の通知（§16.5）は音の ON/OFF と関係なく出す。

### 17.4 順番
- **読み上げはすごろくと一緒に作る**（U-01 の中。§16.6）。
- **まずブラウザの読み上げで動かし**、**VOICEVOX の準備ができたら `/api/tts` につなぐ**。
  - 【仮定】試験では VOICEVOX を使わない（エンジンを試験の前提にしない）。`/api/tts` は、エンジンの代わりに 127.0.0.1 の一時ポートで動かす偽のエンジンで、正常（WAV）と停止（503）を確かめる。VOICEVOX が動く PC では手動で鳴らして確認し、結果を試験結果に書く。

### 17.5 制約との関係
- VOICEVOX エンジンは同じ PC の `127.0.0.1` で動くため、「外部 API・クラウド・ネット」には当たらないと考える【仮定】。
- VOICEVOX ENGINE のライセンス（LGPLv3）は OSS の許可リスト（MIT/BSD/Apache/ISC）の外。【仮定】npm の依存として入れず、提出物にも含めず、利用者が別に起動したエンジンを HTTP で呼ぶだけなので、許可リストの「導入する OSS」には当たらないとして扱う。`外部リソース.md` の「npm 以外」に、使い方と条件を M3 で書く。これが認められない場合は、§17.2 のブラウザの読み上げだけにする（Must は削らない）。
- 声の利用規約（各キャラクター）と表示の文言は `音声合成の準備.md` に従う。

### 18.2 組み込み
- **4枚とも `<img>` で出す**（インラインの SVG にしない）。
- 形式: `viewBox="0 0 120 120"`、`width="120"`・`height="120"`。**背景は透明**。**体は中央**で、**足元は y=112**。
- **使わないもの**: 外部読み込み・文字（`<text>`）・`id` 属性・`script`・フィルター（`<filter>`）。【仮定】あわせて `<style>`・`style` 属性・イベント属性（`onload` など）・`<image>`・`<use>`・グラデーションも使わず、色は `fill`・`stroke` の属性で直接書く（`id` が無いと参照ができず、`<img>` の中では CSS も効かないため）。
- **読み上げ中の口パク**: 今の表情と、その talk の絵を **0.15秒ほどで交互**に出す（§17.3）。**しゃべっていない時は talk を出さない**。
  - 【仮定】交互の切り替えは2枚の `<img>` を重ね、外部 CSS のクラスで片方を見せる（インラインの style を使わない。CSP）。2枚の位置がずれないよう、talk は元の絵と同じ大きさ・同じ位置で描く。
- **talk は元の絵と口以外を全く同じ**にする。口は **「閉じた形」（元の絵）と「大きく開けた形」（talk）** で差をはっきりさせる。
- **準備中のシルエットは CSS で作る**（絵は別に作らない）。だから**輪郭だけでだれかわかる形**にする。
  - 【仮定】CSS の `filter: brightness(0)` と薄い色で happy の絵を塗りつぶして使う（ここでのフィルターは SVG の中ではなく画面の CSS なので、上の「フィルターは使わない」とは別）。輪郭の手がかりの見込み: ともにゃんは猫の耳としっぽの灯り、ほしろうは星の形の髪か帽子、ぴっこんは頭の羽と左右に張ったひれと平たい足（正面向きのくちばしは輪郭に出ない）、とうじいは見回りの笠とつえ。形は各チャットで決める。
  - シルエットには「準備中」と、だれかを文字で添える（色や形だけに頼らない。WCAG 1.1.1・1.4.1）。

### 18.3 絵柄（4体で共通）
| 項目 | 決まり |
|------|--------|
| 体の比 | **2等身のちびキャラ**。**頭は体の1.5倍の丸** |
| 目 | **縦長の楕円**、幅は**顔幅の約2割**。**顔の下半分より**に、**左右を広めに離す**。**白いハイライトを大小2つ** |
| 口・鼻 | **小さく** |
| 頬 | **薄いピンクの楕円** |
| 線 | **太さ 2.5**、**端と角を丸く**（`stroke-linecap="round"`・`stroke-linejoin="round"`）。**黒でなく濃い色** |
| 塗り | **平ら**、**陰は1段だけ** |
| 先端 | **耳や角の先は丸く** |
| 色数 | **1体5色まで** |

【仮定】
- 指示の「左右を広めに話」は「離す」と読んだ。
- 「頭は体の1.5倍」は、頭の高さ（直径）が首から下の高さの1.5倍、と読む。
- 色数の5色には、線・塗り・陰の色を数え、**目のハイライトの白と頬のピンクは数えない**（どの体にも共通の飾りのため）。数え方は各 `メモ.md` に書く。
- 線の濃い色は、その体の塗りの色を暗くした色にする（例: 黄色の体なら濃い茶色）。
- 4体の色は互いに見分けやすく（色の名前で言い分けられる程度）、線の色と背景（白と画面の淡い色）のコントラストは 3:1 以上を目安にする（WCAG 1.4.11）。

### 19.10 特典
- 上に、取ったスタンプの数。
- クーポンはチケットの形のカードにする: 名前、状態（**使える／次に来た日から／利用済み**）、使えるお店、期限、使い方。新しく取ったものに「NEW」。

### 19.11 設定
- **ことば**: 標準語・ひらがな・English。ひらがなでは**漢字に `ruby` でふりがな**を付ける。プルダウンの選択肢と入力欄の見本の文は `ruby` が使えないため、ひらがなに置き換える【仮定】。
- **文字サイズ**: 小・中・大（モックでは 15・17・20px）。
- **音声**: 読み上げ あり/なし、効果音 あり/なし（効果音は Web Audio で作る短い音）。
- **すごろく**: 遊ぶ/遊ばない。**遊ばないと、すごろくへの入り口を隠す**。隠すのは、下のメニューの「遊ぶ」、ホームの「すごろくの続き」、「すごろくで遊ぶ」、「＋1 さいころ」の表示。QR・ひとこと・誘うの後はすごろくへ進まず、詳細にもどる【仮定】。
- **選んだ内容はすぐに反映**する（保存ボタンなし）。下のボタンは「この設定でもどる」。

### 19.12 前の節との関係
- §4 の文字サイズ（標準・大・特大）は、**小・中・大**に置き換える。§4 の「日本語/英語」は、**標準語・ひらがな・English** に置き換える（ユーザー指示）。
- §16.5 の【仮定】「音の ON/OFF は遊ぶ画面の上」は、**設定の「効果音」「読み上げ」**に置き換える。OFF にしたら再生中の声も止める（§17.3）のは変えない。
- 読み上げが「あり」のときの読み方は §17 に従う（VOICEVOX、代わりにブラウザの読み上げ、すごろくのセリフは操作の後に読む、VOICEVOX の表示）。モックの「自動では読みません」の文言と、まだ無い VOICEVOX の表示は、M3 の画面設計で §17 に合わせる【仮定】。
- すごろくの盤は §16 に従う（縦長の SVG、50マス、飾り、立体のさいころ、ゴールの演出）。モックの20マス・4段は、画面の流れを見るための簡略【仮定】。
- アバターの絵は §18 に従う（`<img>` で4枚）。モックの猫は仮の絵。§15 の予言と答え合わせの画面は、このモックに入れていない（`画面設計/SC-09_予言と答え合わせ.md`）。
- モックは文書なので、CSS と JS を HTML の中に書いた。アプリでは CSP（`script-src 'self'`・`style-src 'self'`）のとおり外部ファイルにする。
- aidlc ルールでは画面モックと画面設計を1対1（`SC-xx_*.html`）にする。今回はユーザー指示で1ファイルにしたので、M3 で画面 ID を振るときに、この1ファイルを全体の流れの見本として残すか、SC-xx ごとに分けるかを決める【仮定】。
