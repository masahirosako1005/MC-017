## 4. 作るもの

### 4.1 データ【仮定。db/schema.sql は本体だけが直す】

- `plans(user_id, spot_id, created_day, status 'open'|'done')`: 1人 open 3件まで。QR を読んだ日に `done`。
- `campaigns(id, shop_id, kind 'item'|'yen'|'percent', item_key?, value?, starts, ends, status 'draft'|'pending'|'active'|'rejected'|'ended', created_day)`: 1店あたり確認待ち＋実施中は合わせて1つまで。
- `board_extras(user_id, board_no, campaign_id, square)`: 利用者×盤×キャンペーンで1行（同じマスに戻る）。
- `coupons` に `campaign_id`（NULL 可）を足し、`template_id` の許可に `'campaign'` を足す。

### 4.2 特典の選択肢（自由入力なし。【仮定】品は見本）

| 店 | 無料・サービス（`item`） | 円引き（`yen`） | %引き（`percent`） |
|----|--------------------------|-----------------|--------------------|
| s8 あかり堂 | 和紙のしおり、ポストカード1枚 | 100・200・300・500 | 10・20・30 |
| s9 きしめん ひだまり | きしめん大盛り、天ぷら1品、アイス | 同じ | 同じ |
| s11 みそかつ こもれび | みそかつミニ1切れ、コーヒー1杯 | 同じ | 同じ |

- 表示名はサーバーが決める（例「コーヒー1杯 無料」「100円引き」「アイス サービス」）。他店の名前や連絡先を書けないので、名前の検査は要らない。
- 自店だけ: URL の `:shopId` が `X-Operator` の店と同じときだけ作れる（違えば 404）。本文に店の項目を持たせない（`z.strictObject`。持たせたら 400）。`coupons.shop_id` は `campaigns.shop_id` から決める。

### 4.3 動き

1. 利用者がスポット詳細で「次に行く予定に入れる」を押す（`plans`）。
2. 店が SC-A13 で、近くの予定が**閾値（10人。定数）以上**のときだけ、品か割引を選び、開始日（明日以降）・終了日（7〜30日）を決めて作る。5人未満は「5人未満」とだけ出し、合計は「n人以上」。
3. 承認（b を採るとき）。観光協会が承認すると、開始日に `active`。b を外したときは作った時点で `active`（開始日から）。
4. 盤: `active` のキャンペーンがあるとき、対象（店から 2.5km 以内のスポットに open の予定がある人）の盤に🏪を置く。位置は今の位置の3〜10マス先のふつうのマスから**決まった計算**（利用者・キャンペーンで固定）。🎁・スポット・季節・ゴールは置き換えない。1枚の盤に最大2つ。
5. 止まったら、翌日から終了日まで使えるクーポンを出す（`coupons`・同じ盤の同じマスは1枚）。

### 4.4 API【仮定】

| メソッドとパス | 中身 | 役割 |
|----------------|------|------|
| `GET /api/admin/summary?days=` | K-01・K-02・K-03・K-07・段ごとの人数。`days` は 7・28・90（c）。既定は全期間 | association |
| `GET /api/admin/shops/:shopId/summary` | 自店のクーポン（配った・使われた・止まった人）（a） | association か、その店 |
| `GET /api/admin/shops/:shopId/demand` | 近くのスポットごとの予定人数（5人未満は隠す）、作れるか | その店 |
| `GET・POST /api/admin/shops/:shopId/campaigns` | 一覧・作成（`{ requestId, kind, itemKey?, value?, starts, ends }`） | その店 |
| `GET /api/admin/campaigns?status=pending` ・ `POST /api/admin/campaigns/:id/approve｜reject`（b） | 確認待ちの一覧・承認・差し戻し | association |
| `GET・POST /api/plans` | 利用者アプリ。予定の一覧・追加（open 3件まで） | ゲスト |

- すべて `ADMIN_MODE=1` のときだけ登録（`/api/plans` は常時）。役割は `X-Operator`（`association`・`shop-s8`・`shop-s9`・`shop-s11`）を zod で検証。他の役割は 404。応答に利用者 ID を含めない。

## 5. 指標（現状の分析。1時間版）

| ID | 指標 | 数え方 |
|----|------|--------|
| K-01 | 利用者数 | `visits` が1行以上ある利用者 |
| K-02 | 再訪率 | `visits.kind='revisit'` がある人 ÷ K-01 |
| K-03 | 次の理由の保有率 | その日の終わりに、盤が途中（1〜44マス）／open の予定／翌日以降に使えるクーポンの**どれか**を持つ人 ÷ その日の利用者 |

| d | 気づき1件 | K-03 が前の期間より5ポイント以上下がったら「帰るときに次の理由を持っている人が減っています」 |

- 予言は管理サイトに出さない（16:17 の指示）。K-03 の「理由」は予言ではなく「次に行く予定」。

## 6. 試験で確かめる観点（合否は書かない。実装後に T を採番）

- 指標: 決まった小さいデータで K-01・K-02・K-03・K-07 が手計算と一致。旅の2日目（`day2`）は再訪に数えない。7日ちょうどは再訪。
- 個人情報: 応答に `guest-` の ID が含まれない。5人未満が数字で出ない。
- 自店だけ: 他店の `:shopId` で作る・本文に `shopId` を入れる・`X-Operator` が違う、が 404／400。他店のクーポンが盤に出ない。
- 閾値: 9人では作れず、10人で作れる。5人未満の内訳は「5人未満」。
- 盤: 🎁・スポット・ゴールを置き換えない。同じ利用者・同じキャンペーンで毎回同じマス。1枚の盤に最大2つ。止まると翌日から使えるクーポンが1枚だけ出る（二重に出ない）。
- 承認（b）: 承認前は盤に出ない。差し戻しは出ない。
- 入力: 開始日が今日以前、終了日が7日未満・31日以上、`itemKey` がその店の許可リスト外、未知キー、が 400。
- 権限: `ADMIN_MODE` なしで `/admin`・`/api/admin/*` が 404。
- アクセシビリティ: プルダウンと主ボタンがキーボードで使える、差は記号と文字、200% 拡大で横に流れない。

## 7. 【仮定】

- 閾値は10人（仕様案 §11.3 の既定）。設定の画面は作らず、定数にする（SC-A07 は範囲外）。
- 1枚の盤に🏪は最大2つ（仕様案は3つ）。1店あたりの同時の数は1つ。
- 承認を外したとき（b を採らない場合）は、作った時点で `active` にする。選択式なので誤解を招く文は作れない。
- 店の品の一覧（§4.2）は見本。実際の店のメニューに合わせて直す。
- 利用者アプリの「次に行く予定」の取り消しは作らない（open 3件の上限だけ）。
- 管理サイトの文言は日本語のみ（仕様案 §5.1）。
